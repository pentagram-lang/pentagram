# Command Plane

The command plane provides the repository's operational commands for formatting, checks, tests, agent launch, the boot shell, watch mode, and project-control access.

## Identity and ownership

The command-plane Python package is `zero/`. Its package entrypoint is `zero/__main__.py`. The Nix profile exposes the entrypoint as both `zero` and `0`; both names execute the same command plane. `0` is the working command name used in repository documentation and automation.

The project-control subsystem is not owned by the command plane. Its implementation and tests live in `proj/`, and the command plane invokes it through the `0 proj` command group.

The project command group owns the operational interface for the project’s active goal. Goal text is read from the project database rather than copied through an agent prompt. Agents that can activate a goal use the exact output of `0 proj goal text NAME`. When an agent cannot activate a goal, it asks the operator to run the exact command `0 proj goal copy NAME`; the project subsystem emits the canonical text through OSC 52 clipboard control characters.

The former `pt` command is not installed or accepted as an alias.

## Launcher contract

The installed wrapper searches from the current directory toward the filesystem root for a repository containing `zero/__main__.py`. It changes to that repository root and runs the Python package entrypoint. This keeps commands independent of the caller's working directory while making the repository boundary explicit.

The `0 a flash` launcher always creates a temporary AGY custom-agent adapter containing `sys.md` with the checked-in tool list in `zero/agent.py`. Because AGY custom agents default to an empty tool list, the adapter explicitly enables the file, shell, web, image, scheduling, delegation, and question tools. Before creating that adapter, the launcher runs a mandatory filesystem-only AGY preflight. It scans operator-home `~/.gemini/config/skills/` and paths registered by `~/.gemini/config/skills.json`, including inherited configurations, and blocks any discovered standalone skill because AGY has no persistent all-skills disable setting. It scans `~/.gemini/config/plugins/` and paths registered by `~/.gemini/config/plugins.json`, including inherited configurations, reads each `plugin.json`, and requires each effectively installed plugin to be disabled by the `plugins` map in `~/.gemini/config/config.json` or by a manifest-level `disabled: true` fallback. It does not run `agy plugin list`. It scans `~/.gemini/config/mcp_config.json` and blocks every configured standalone MCP server because AGY has no reliable persistent all-MCP disable setting; MCP servers packaged by disabled plugins are covered by the plugin check. The preflight does not inspect launcher arguments or harness environment variables, and it does not check AGY memory because AGY has no user-facing memory subsystem. Bundled skills under `~/.gemini/antigravity-cli/builtin/skills/` and ambient `AGENTS.md`/`GEMINI.md` instructions remain separate residual authority; project, repository, ancestor, managed, and system paths remain task 13 scope. Set `PENTAGRAM_AGY_TOOLSET` to enable a separate default-auth AGY `--print --output-format stream-json` tool-surface preflight; the launcher then fails if any checked-in tool is absent from AGY's `init.tools` inventory. The variable never changes the adapter's tool list, and additional AGY backend components are allowed because they are not all valid custom-agent frontmatter tools. `--dangerously-skip-permissions` removes approval prompts for the launched session; it does not override the repository contract or authorize commits, unrelated scope, or destructive operations.

The Codex launchers run a mandatory filesystem-only ambient-authority preflight before starting Codex. It reads the Codex home and project configuration files and the home-level non-plugin Codex skill files; it does not start Codex or contact a network service. Codex represents a disabled feature either with `false` or by omitting the feature key, so both forms pass the preflight. Every configured top-level MCP server must be disabled. Every home-level `~/.codex/skills/**/SKILL.md` must be disabled through the `/skills` menu. Any file under home-level `~/.codex/memories` blocks launch because Codex has no persistent setting that disables those files; remove or rename the file. Codex execution-policy `.rules` files are a separate control surface and are not checked as memory files. Plugin cache contents and plugin-provided MCP settings are excluded because `features.plugins` is disabled. The preflight does not inspect launcher arguments or harness environment controls; those are forwarded unchanged to Codex. Feature findings provide the persistent `codex features disable memories` or `codex features disable plugins` command; MCP findings identify their persistent TOML entries. Any failure stops the launcher before the Codex process is replaced.

The Claude launchers run the same kind of filesystem-only persistent-state preflight. It reads Claude settings, `~/.claude.json`, the project `.mcp.json`, and the home-level standalone skill and memory files; it does not start Claude or inspect launcher arguments or harness environment controls. Every home-level `~/.claude/skills/**/SKILL.md` must be removed or renamed because Claude has no persistent setting to disable standalone skills. Any home-level `~/CLAUDE.md`, `~/.claude/CLAUDE.md`, or `~/.claude/rules/**/*.md` memory file also blocks launch because Claude has no persistent setting to disable those files. Auto-memory must be persistently disabled with the `/memory` setting, every configured plugin must be disabled through `/plugin`, and every MCP in the hardcoded Claude MCP set or persisted MCP configuration must be disabled through `/mcp` in the corresponding persisted disabled list. Set `PENTAGRAM_CLAUDE_MCP_SET` to enable a zero-specific `claude mcp list` inventory check; the launcher then fails if the live inventory differs from the hardcoded set. Plugin-provided skills and MCP settings are excluded when all configured plugins are disabled. Any failure stops the launcher before the Claude process is replaced.

These standalone skill and memory-file checks are limited to the operator's home paths. Project and repository `.claude`/`.agents` paths, ancestor `CLAUDE.md` files, managed or system paths, and other repository policy surfaces are outside these launcher preflights.

The standalone `0 check doc` command runs the Markdown checks in the [lint document](../doc/quality/lint.md) and reports its own timing. The standalone `0 check commit` command validates commit-message line lengths and reports its own timing. The complete `0 check` cycle runs both steps when commit validation is enabled, together with the command-plane tests and a repository policy scan over Git-tracked files and untracked files that are not excluded by Git's standard ignore rules. Using Git's inventory prevents `.ignore` and `.rgignore` from hiding prohibited paths, excludes the `.git` tree, and includes tracked and untracked symbolic links. The scan rejects the file basenames `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `CLAUDE.local.md`, and `GEMINI.md`, plus any path containing an `.agents`, `.claude`, `.codex`, or `.gemini` component. These broad path rules cover nested skill, agent, rule, and command surfaces without banning generic names such as `SKILL.md`, `skills`, `agents`, or `rules` elsewhere. Harnesses can be configured with arbitrary alternate instruction filenames; this fixed-name repository scan does not attempt to infer those operator-specific names.

## Command boundary

The command plane owns operational orchestration and delegates domain behaviour to the subsystem that owns it. It does not duplicate the project database schema or lifecycle rules; `proj/project.py` remains the source of truth for those rules.
